# 🚀 ECS CI/CD パイプライン全体像まとめ

ローカルでの開発から、AWS ECSへ自動デプロイされるまでのプロセスを整理しました。

## 1. ワークフローの概要

| ステップ | フェーズ | 場所 | アクション |
| --- | --- | --- | --- |
| **1** | **開発** | ローカル | `index.html` を修正し、`git push` でGitHubへ送信。 |
| **2** | **ビルド & 送信** | GitHub Actions | Dockerイメージをビルドし、**Amazon ECR** へプッシュ。 |
| **3** | **書き換え** | GitHub Actions | `task-definition.json` 内の `image` 項目を、手順2の最新URLに書き換える。 |
| **4** | **登録（デプロイ）** | **GitHub ➡️ AWS** | 書き換えたJSONをAWSへ送信。**新しい「リビジョン」**として登録される。 |
| **5** | **入替** | AWS ECS | サービスが更新を検知。古いコンテナを停止し、新しいコンテナを起動する。 |

---

## 2. タスク定義が更新されるタイミング

疑問点であった**「`task-definition.json` はいつAWSにプッシュされるのか？」**の回答です。

### 登録の瞬間

GitHub Actions の **`Deploy to Amazon ECS`** ステップが実行された瞬間に、AWSのAPIを通じてプッシュされます。

* **入力:** 最新のDockerイメージURLが埋め込まれたJSONファイル。
* **処理:** AWS側で「リビジョン番号」が1つ繰り上がります（例：`v2:1` ➡️ `v2:2`）。
* **結果:** この新しい「設計図（リビジョン）」を元に、新しいコンテナが立ち上がります。

---

## 3. 各コンポーネントの役割

### 📂 タスク定義 (`task-definition.json`)

**「コンテナの設計図」**です。

* どのDockerイメージを使うか（ECRのURL）。
* CPUやメモリの割り当て。
* 開放するポート番号（例：80番ポート）などの情報。

### ⚙️ ECS サービス

**「コンテナの管理人」**です。

* 指定した数のコンテナ（タスク）が常に動いているか監視。
* 新しい「設計図（リビジョン）」が登録されると、自動で**ローリングアップデート**（コンテナの入れ替え）を実行します。

### 🌐 パブリック IP

**「サイトの玄関口」**です。

* Fargateの場合、新しいコンテナが起動するたびに新しいパブリックIPが割り振られます。
* **AWSコンソール > タスク > ネットワーク** タブから最新のIPを確認できます。

---

## 4. 現在のチェックポイント

自動更新が反映されない場合に確認すべき点です：

1. **イメージタグの固定:** JSON内で `:v2` のようにタグが固定されていると、ECRを更新しても古いイメージが呼ばれ続けます。
2. **Local vs Cloud:** `localhost` は自分のPC。CI/CDの成果を見るには必ず **AWSのパブリックIP** を確認する必要があります。
3. **反映のタイムラグ:** AWS側でコンテナが完全に入れ替わるまで、通常2〜3分かかります。
