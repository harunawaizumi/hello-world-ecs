# 🚀 ECS CI/CD パイプライン全体像まとめ

ローカルでの開発から、AWS ECSへ自動デプロイされるまでのプロセスを整理する。

## 1. ワークフローの概要

| ステップ | フェーズ | 場所 | アクション |
| :--- | :--- | :--- | :--- |
| **1** | **開発 (CI)** | ローカル | コードを修正し `git push` を実行。 |
| **2** | **ビルド (CI)** | GitHub Actions | Dockerイメージをビルドし、**Amazon ECR** へプッシュ。 |
| **3** | **検証デプロイ (CD)** | GitHub Actions | **Staging（テスト環境）** サービスを自動更新。 |
| **4** | **目視確認** | ブラウザ | AWS上のテスト環境用URL（パブリックIP:ポート）へアクセスし、サイトが正しく更新されているか目視で確認。 |
| **5** | **手動承認** | GitHub | 内容に問題がなければ、GitHub Actions 上に表示される **「承認ボタン」** をクリック。 |
| **6** | **本番デプロイ (CD)** | GitHub Actions | 承認後、直ちに本番用のサービスが更新され、新しいバージョンが公開される。 |

## 2. タスク定義が更新されるタイミング

**「`task-definition.json` はいつAWSにプッシュされるのか？」**。

### 登録の瞬間

GitHub Actions の **`Deploy to Amazon ECS`** ステップが実行された瞬間に、AWSのAPIを通じてプッシュされる。

* **入力:** 最新のDockerイメージURLが埋め込まれたJSONファイル。
* **処理:** AWS側で「リビジョン番号」が1つ繰り上がります（例：`v2:1` ➡️ `v2:2`）。
* **結果:** この新しい「設計図（リビジョン）」を元に、新しいコンテナが立ち上がる。

---

## 3. 各コンポーネントの役割

### 📂 タスク定義 (`task-definition.json`)

**「コンテナの設計図」**。

* どのDockerイメージを使うか（ECRのURL）。
* CPUやメモリの割り当て。
* 開放するポート番号（例：80番ポート）などの情報。

### ⚙️ ECS サービス

**「コンテナの管理人」**。

* 指定した数のコンテナ（タスク）が常に動いているか監視。
* 新しい「設計図（リビジョン）」が登録されると、自動で**ローリングアップデート**（コンテナの入れ替え）を実行します。

### 🌐 パブリック IP

**「サイトの玄関口」**。

* Fargateの場合、新しいコンテナが起動するたびに新しいパブリックIPが割り振られます。
* **AWSコンソール > タスク > ネットワーク** タブから最新のIPを確認できます。

## 4. 現在のチェックポイント

自動更新が反映されない場合に確認すべき点：

1. **イメージタグの固定:** JSON内で `:v2` のようにタグが固定されていると、ECRを更新しても古いイメージが呼ばれ続けます。
2. **Local vs Cloud:** `localhost` は自分のPC。CI/CDの成果を見るには必ず **AWSのパブリックIP** を確認する必要があります。
3. **反映のタイムラグ:** AWS側でコンテナが完全に入れ替わるまで、通常2〜3分かかります。

---


## 5. 設定のポイント
- **`environment: production`**: GitHubのEnvironment機能を利用し、承認フローを有効化。
- **OIDC連携**: AWSアクセスキーを直接GitHubに保存せず、短期間のみ有効なトークンを発行する安全な認証方式（IAM Role）を採用。
- **タスク定義の動的置換**: ビルドごとに生成される固有のイメージタグ（Commit SHA）をタスク定義に埋め込むことで、環境間でのイメージの不一致を防止。
